# 架构与原理

这份文档解释**为什么是这个做法**，以及每个约束背后的实测依据。目标只有一件事：
在豆包自己的窗口里播一段片头，然后让它**从模糊里浮出来**。所有方案选择都服从豆包的
客户端形态，不借用其它客户端的假设。

## 1. 目标客户端：豆包桌面端是什么

在动手前先量过，而不是猜：

| 事实 | 实测 |
|---|---|
| 外壳 | 自绘 Chromium 壳：`Doubao.exe` + `Doubao.dll`（323 MB），Chromium **147.0.7727.149** |
| 版本 | 豆包 **2.33.5**（`Application\app\manifest.json`） |
| 资源形态 | **没有 `app.asar`**、没有 `resources` 目录、没有 JS 可改 |
| 界面 | `chrome://doubao-chat/chat` 里的 React 应用（`#root`），以及一个 `doubao://doubao-background/` 背景页 |
| CSP | 该特权页**没有 CSP meta** |
| 调试端口 | 认 `--remote-debugging-port`，1.4 秒就绪 |

### 由此排除掉的方案

- **改 `app.asar`**：不存在，先排除。
- **装扩展**：Doubao 自带若干 `chrome-extension://` 组件，但页面是 `chrome://` 特权页，
  内容脚本**不允许**注入这类页面。排除。
- **改主程序 / 签名**：要碰安装目录、会破坏签名、每次更新失效。不做。
- **外部全屏浮层窗口**：可行，但那是"盖住整个屏幕"的启动器，会连任务栏一起盖住，
  而且和豆包窗口的缩放/拖动脱节，不像"应用自己的开机动画"。

### 剩下的唯一正解

用 Chromium 自带的 **DevTools 协议**：正常启动豆包，附加到主窗口页面，在页面内部
挂浮层。这样浮层是**豆包窗口的一部分**（跟随窗口、跟随缩放、盖住它自绘的标题栏），
而豆包的文件一个字节都没变。

## 2. 生命周期

```
launch.vbs
  └─ node bin/inject.mjs
       ├─ 读 config.json，校验视频
       ├─ 找 Doubao.exe（配置 → 常见安装路径）
       ├─ 检测单实例（tasklist）——在跑就直接提示，不假装
       ├─ 选一个空闲端口（0 → 内核分配）
       ├─ spawn Doubao.exe --remote-debugging-port=<port> --remote-debugging-address=127.0.0.1
       ├─ 轮询 /json/version（≤20s）
       ├─ 轮询 /json/list，挑主窗口目标（URL 优先，标题兜底）
       ├─ CDP 连接 → Runtime.enable
       ├─ 等窗口可见（Browser.getWindowForTarget，≤15s；一直最小化就不播）
       ├─ 起本地视频服务（127.0.0.1，随机端口，只服务 /boot.mp4，支持 Range）
       ├─ Runtime.evaluate 注入浮层（awaitPromise，等它播完）
       ├─ 浮层自己完成退场并清理，返回 { ok, reason, ms }
       ├─ 关视频服务、关 CDP
       └─ 退出（豆包继续运行）
```

**任何一步失败都不会杀掉豆包、不会阻塞它启动。** 动画是附加效果，不是启动的前提：
20 秒等不到调试端点，就只写一条日志然后退出，豆包照常可用。

## 3. 视频怎么送进特权页（v0.2.0：内联 blob，不走网络）

第一版是在本机起一个 HTTP 服务，让 `<video>` 去拉。**在冷启动下这条路很糟**，实测：

| 阶段 | 本机 HTTP | 内联 blob |
|---|---|---|
| 请求真正到达 | 注入后 **+3.2 秒**（被应用自己的启动资源挤在队列里） | 不存在请求 |
| `loadedmetadata` | **4017ms** | **68ms** |
| `playing`（首帧） | **4144ms** | **261ms** |

也就是说，第一版在用户眼里是"**黑屏 4 秒**然后才动"。原因不在文件大小（2.9MB），
而在这个自定义 Chromium 壳启动瞬间的渲染进程负载：媒体请求要排在应用自己的几百个
资源请求之后。豆包页面没有 CSP，但这不代表请求会按时发生。

所以现在把字节直接 base64 传进页面：

```
node 读文件 → base64 → Runtime.evaluate（表达式里带字符串）
   → 页面内 atob（4ms）→ Uint8Array（33ms）→ Blob → createObjectURL → <video src>
```

代价与约束：

- 视频常驻内存，所以有 `maxVideoMB`（默认 30MB）卡口，超了直接报错并给出压缩命令；
- 一次 CDP 消息变大（2.9MB 视频 ≈ 3.9MB 表达式），但换来的是**可预测的百毫秒级起步**；
- 用完 `URL.revokeObjectURL()`，不给页面留垃圾。

## 3.5 声音：为什么要改启动参数

"刚启动、没有任何用户手势"正是 Chromium 自动播放策略要拦的场景：带声音的 `play()`
会抛 `NotAllowedError`。这里不是想办法绕浏览器，而是**控制启动命令**——本项目本来就
负责启动豆包，于是加上：

```
--autoplay-policy=no-user-gesture-required
```

实测结果：`muted:false / volume:1 / soundBlocked:false`，首帧即有声。

三层兜底：

1. 标志生效 → 直接出声；
2. 标志被覆盖（企业策略等）→ `play()` 被拒 → **自动退回静音播放**，提示
   「点击开启声音 · 再点任意处跳过」，第一次点击开声音，再点才跳过；
3. 退场时音量在 `handoffMs` 内线性淡出到 0，避免"画面在过渡、声音被掐断"。

**响度也是内容的一部分**：源片实测 **-36.0 LUFS / -15.3 dBTP**（AI 生成视频常见），
在笔记本上几乎听不见。仓库里的 `assets/boot.mp4` 已用 `loudnorm` 拉到
**-16.3 LUFS / -1.4 dBTP**，并保留视频流原样（`-c:v copy`）。

## 4. 视觉：为什么是"虚化淡出"而不是淡出到黑

退场分两层，同时进行：

| 层 | 动作 | 时长 |
|---|---|---|
| 视频 | `opacity → 0`、`blur(16px)`、轻微 `scale(1.02)` | 460ms |
| 整层 | 底色由黑转透明；`backdrop-filter: blur(18px) → blur(0)` | 460ms |

关键在**模糊在视频背后**：第一帧视频还盖着（模糊看不见），等视频透明时模糊已经在退，
于是豆包是"先糊后清"浮出来的，而不是从黑幕后面弹出来。

两条都是实测踩出来的：

- **模糊必须用 `@keyframes` 而不是 transition**：只有动画能表达"18px → 0"的衰减；
- **计时必须比 CSS 长**：`handoffMs = 520` > `460`。把过渡半路切断，比没有过渡更难看。

进度条/看门狗：

- `firstFrameMs`（默认 8s）内拿不到首帧 → 强制交接，绝不把界面扣在黑色上；
- `video.error` → 立即交接；
- 自动播放被拒（静音播放极少见）→ 3 秒后交接。

## 5. 豆包专属的四件事

这四条是豆包独占的坑 —— 通用做法（把浮层当普通网页叠上去）在这里会翻车：

1. **「跳过」放右下角。** 豆包把窗口按钮（最小化/最大化/关闭）**画在页面右上角**。
   浮层盖住整个页面后，右上角的「跳过」会正好压在关闭键上：想关窗口的人先点到跳过。
   所以跳过放右下，并且 Esc 常驻。
2. **等窗口可见再播，但别用浏览器窗口 API。** 最小化/托盘状态下 `video.play()` 会成功但画面
   被节流，等于"在看不见的地方放完了"。这里用 `document.visibilityState` 判断：
   `Browser.getWindowForTarget` 对豆包**永远返回 `Browser window not found`**——它没有把窗口
   注册进 Chromium 的浏览器窗口模型（自绘外壳，实测）。超时（15s）就干脆不播。
3. **覆盖豆包自绘的标题栏与侧栏。** 因为浮层在页面内且 `z-index` 顶格，
   它天然盖住豆包自己画的窗口控件——这是"看起来像应用的一部分"的前提。
4. **单实例要先检测。** 豆包已经在跑时，带端口启动会被转交给已有进程，
   端口不会生效。与其"启动了但没动画"，不如明确提示先退出豆包。

## 6. 设置与片库：为什么是独立窗口，而不是动画里的按钮

片头画面里**只有一个「跳过」**。选片头、调音量、改铺满方式，全部在独立的设置页里。

理由有三条，按重要性排：

1. **动画是"产品的一部分"，设置不是。** 播放中的浮层一旦多出按钮，它立刻变成"一个工具
   的弹窗"，而不是"应用自己的开机画面"。这是观感问题，也是这个项目存在的意义。
2. **豆包没有插件设置页可挂。** 它在设置页里塞条目的唯一办法是注入它自己的 React 路由，
   那既脆弱（更新即坏），也违背"不改豆包界面"的前提。所以设置必须自成一体。
3. **选片头是启动之前的事。** 为了改配置去启动一次豆包、加调试端口、注入浮层，成本和
   风险都不划算；豆包正开着（正常方式启动）时还根本连不上。

实现上是一个**一次性本地服务**：`设置.vbs` → `node bin/settings.mjs` → 在 `127.0.0.1`
随机端口上起服务 → 用默认浏览器打开 `http://127.0.0.1:<port>/?t=<一次性 token>`。
关掉页面或 10 分钟无操作，服务退出。

- 绑定 `127.0.0.1`，端口随机；
- 所有请求校验 token（GET 页面、API、媒体预览都要）；
- 只列 `clips/` 里的视频、只写 `config.json` 的已知字段、只服务这些文件；
- 写配置是**原子**的（临时文件 + rename）：注入器可能同时正在读它。

**片库没有数据库**：`clips/` 里放一个 mp4 就等于多一套动画，删掉就等于移除。`clips.json`
只是可选的展示名/备注，不参与"有哪些片"的判定——否则用户新丢进去的文件会因为没登记而
"看不见"，那正是最该避免的坑。

## 7. 安全模型

- 端口只绑 `127.0.0.1`；`--remote-debugging-address=127.0.0.1` 显式写死，避免误绑 `0.0.0.0`。
- 端口每次随机；注入器退出后不可再用（豆包进程里那个端口还开着，这是 Chromium 的限制，
  见下面的"诚实说明"）。
- 本地视频服务也只在 `127.0.0.1`，只服务一个文件，动画结束即关闭。
- 不联网：注入器只有 `fetch` 到 `127.0.0.1:<port>` 的请求。

**诚实说明**：豆包运行的整个期间，调试端口都在。本机上的其它程序理论上可以连上它并
操控豆包界面。这是 Chromium 调试端口的固有性质；任何"启动时注入"的工具都绕不开。
从普通豆包快捷方式启动则完全没有这个面。项目不为此做隐藏或美化。

## 8. 已验证 / 未验证

已验证（本机，豆包 2.33.5 / Chromium 147）：

- 调试端口被接受，`/json/version` 与 `/json/list` 正常；
- 主窗口目标正确识别（`chrome://doubao-chat/chat`）；
- 特权页内注入 DOM + 内联样式成功（无 CSP 拦截）；
- 内联 blob 播放：`loadedmetadata` 68ms、`playing` 261ms，`1280x720 / 8.1s`；
- 有声播放：`muted:false / volume:1`，`--autoplay-policy` 生效；
- 浮层整窗覆盖（截图），退场 230ms 时呈"应用强模糊"（截图）；
- 退场后 `#dba-root` 与样式表都被移除，注入器 exit 0；
- 单实例检测、页面可见性等待、失败不阻塞豆包启动；
- 端到端自检 `npm run smoke` 全绿。

未验证 / 明确不知道：

- 豆包其它版本（尤其更新后）页面地址或窗口按钮布局变化时的行为；
- macOS 客户端（路径、进程名、启动参数都不同）；
- 多显示器 / 高 DPI 的边界情况（浮层用百分比尺寸，理论上跟随窗口，但没有逐一实测）；
- 企业策略/系统层面强制拦截自动播放时，`--autoplay-policy` 是否还能生效（有静音兜底，但未实测）；
- 豆包自身的异常检测是否会把"带调试端口启动"当作异常（目前无提示、无副作用）。
